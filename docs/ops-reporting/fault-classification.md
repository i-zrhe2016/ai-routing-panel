# 故障判定规则边界

> 权威范围：Prometheus-only 规则能判定和不能判定的事项

规则只接收报告窗口内的 Prometheus range query 结果、目标抓取健康和规则版本参数。缺失样本必须保持为 `unknown`，不得转换为零或正常。

## 可判定能力

| 能力 | 最低指标证据 | 允许结论 |
| --- | --- | --- |
| exporter 抓取连续性 | `up`、抓取持续时间与样本覆盖率 | `normal` / `unknown` |
| 节点可达性 | 独立 blackbox 探针连续失败 | `suspected`；与服务指标共同失败时可为 `fault` |
| Xray 运行状态 | 专用 exporter 的进程/服务状态指标 | 连续失败达到阈值时为 `fault` |
| 流量连续性 | 单调累计连接数或字节数的 `rate`/`increase` | 报告流量空档；不能单独证明故障 |
| 资源风险 | CPU、可用内存、文件系统使用率 | 持续越界时为 `suspected` |
| DNS/AI 回退 | 控制面导出的切换状态与原因指标 | 健康失败触发切换时为 `fault` |

默认严重度为 `fault > suspected > unknown > normal`。所有阈值必须版本化并写入报告，修改阈值需要回放历史窗口和重新验收。

## 明确不能判定

Prometheus-only 方案不能判断：具体错误消息、失败请求内容、用户 UUID、访问域名、协议握手原因、容器 stderr、调用栈、配置文件内容或攻击载荷。规则不得把“无流量”写成“服务宕机”，不得把 `up == 0` 单独解释为业务进程故障，也不得生成未经指标证明的根因。

## 证据组合

- `up == 0` 只证明 Prometheus 无法抓取 exporter；先判遥测缺口。
- blackbox 失败只证明探测路径不可达；至少与服务状态或第二独立探针相关联后才确认故障。
- counter reset 应按进程重启或指标重置处理，不能生成负流量。
- 标签缺失、时间序列重复或覆盖率低于 90% 时，相关能力降为 `unknown`。
- 模型文字如被启用，只能解释规则结果，不能改变状态、规则编号或证据。

## 稳定规则编号

| 编号 | 条件 | 结果 |
| --- | --- | --- |
| `OPS-F001` | 服务状态连续失败且独立探针失败 | `fault` |
| `OPS-F003` | 主数据面健康失败触发 DNS 切换 | `fault` |
| `OPS-F004` | AI 上游健康失败触发回退 | `fault` |
| `OPS-S002` | 资源压力持续越界 | `suspected` |
| `OPS-S003` | 独立指标互相冲突 | `suspected` |
| `OPS-U001` | 关键指标覆盖率不足 | `unknown` |
| `OPS-I001` | 无流量但服务与探针正常 | 信息事件 |
